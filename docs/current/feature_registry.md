# Tangerine Feature Registry

> **GENERATED EVIDENCE — do not edit by hand.** This document is
> rendered by `scripts/gen_feature_registry.sh` from
> [`features.toml`](../../features.toml), the machine-readable source of
> truth: the feature ID, the status, the supported targets, and the test
> references. The CI evidence-gate job regenerates it and runs
> `git diff --exit-code`, so a hand-edited or drifted registry cannot
> merge. Every feature appears exactly once with exactly one status;
> the statuses are **mechanically derived** (test-file existence + suite
> membership + the declared CI gates), never hand-asserted, and the
> item-36 **status ladder** is **calculated**, never typed.

## How a status is decided

The generator verifies each row's evidence before it renders:

- every **test reference** must exist in the tree, and every named
  **suite manifest** (`tests/canary/MANIFEST`, `tests/canary_neg/MANIFEST`,
  `tests/arm64/MANIFEST`) must contain the listed file — a listed artifact
  that does not exist fails the generation;
- every named **CI gate** must be a job in `.github/workflows/ci.yml`;
- `implemented` derives to **implemented + test-covered** (committed test
  artifacts exist) or **implemented + unverified** (no committed test
  artifact), never to run-verified.

## The status ladder (the reviewer's item 36)

The ladder position is CALCULATED from the committed evidence (the
typed `status` in features.toml is only the DECLARED input):

| Position | Derivation (what evidence must exist) |
|----------|----------------------------------------|
| `DECLARED` | the row exists in features.toml |
| `IMPLEMENTED` | the declared status is implemented/partial AND every enforcing-code file/dir reference exists in the tree |
| `SEMANTICALLY_CHECKED` | every listed test artifact exists (committed; std modules additionally parse-clean under the E106 sweep) |
| `NATIVE_TESTED` | at least one listed artifact is a native behavior artifact (a `tests/**/*.tg` canary/@test file or a `tests/run_*.sh` gate) |
| `ADVERSARIAL_TESTED` | at least one listed artifact is adversarial (canary_neg / fuzz / differential / slice_safety / *neg* / *litmus*) |
| `TARGET_COMPLETE` | every declared target is a SERVED target (aarch64-apple-darwin, x86_64-unknown-linux-gnu, x86_64-apple-darwin — windows/wasm32 are NOT served) AND a native artifact exists |
| `EXACT_SHA_VERIFIED` | run evidence at a named SHA: `build/release_evidence.json` (written ONLY by `scripts/gen_status.sh --release-evidence`) carries the tested sha + artifact hashes |
| `RELEASE_GATED` | the feature is listed in the release-evidence file's `release_gated_features` — **never derivable from source**, only from the release-run evidence |

The ladder is a monotone chain: a feature at position N holds every
position below N. The top two positions are RUN facts; this
snapshot records source-state facts only, so nothing above
`TARGET_COMPLETE` appears here unless the release-evidence file is
present in the tree.

> **Execution honesty — the CI-artifact evidence model.** A committed
> test artifact is a source-state fact; an observed execution is a run
> fact, and they are separate statuses:
>
> - **implemented + test-covered** — the repo ships a committed test
>   artifact that exercises the feature (a manifest-registered canary, an
>   invariant group, a required gate, an `@test` file, or the self-host
>   compiler kernel itself as the workload). It does NOT claim the
>   artifact has run anywhere.
> - **implemented + run-verified at SHA** — a CI artifact proves the
>   execution at the named commit: the CI pipeline runs the harness and
>   the suites and uploads the tested-SHA snapshot — the
>   `status-snapshot` CI artifact (STATUS.txt generated by
>   `scripts/gen_status.sh` from the tested commit + the test-artifact
>   hashes). **No feature holds this status in this snapshot** — the
>   ladder/CI has not run on the tested tree, so there is no observed
>   successful execution at a named SHA.
>
> This registry records only source-state facts, never run results.

## Legend

| Status | Meaning |
|--------|---------|
| **implemented + run-verified at SHA** | The compiler/runtime implements the feature AND an observed successful execution of its test artifact at the named commit is proven by a CI artifact (the `status-snapshot` generated by `scripts/gen_status.sh` from the tested SHA). **None in this snapshot** — no ladder/CI run has occurred on the tested tree |
| **implemented + test-covered** | The compiler/runtime implements the feature and a committed test artifact exists (manifest-registered canary, invariant group, required CI gate, `@test` file, or the self-host kernel as workload) that exercises it — but no observed execution at this SHA |
| **implemented + unverified** | The compiler/runtime implements the feature; no committed test artifact exercises it |
| **partial** | A working subset exists; the full feature is not present |
| **API-only** | The std module / interface is declared, but the compiler does not wire it into the pipeline and it is not in the bootstrap closure |

Non-implemented rows keep their unchanged statuses (outside the
implemented-feature vocabulary): **design** — specified in docs/RFCs
only, no implementation; **unsupported** — explicitly removed or
rejected by the compiler (E100/E106 hard errors).

## The experimental gate (the reviewer's item 33)

A row marked **experimental** is a platform-only surface whose targets
are unsupported/API-only (the stable-subset policy): the feature and
its std modules (the row's `modules = [...]`) carry parse-clean
evidence only and are **explicitly excluded from the shipped-std
behavior claims** — see the [Stdlib Completeness Model](stdlib_completeness.md)
and the contracts manifest (`docs/current/stdlib_contracts.toml`). The
generator cross-checks the two registries: every experimental module
must be listed in exactly one experimental row, and every module a
row lists must be experimental in the contracts manifest.
