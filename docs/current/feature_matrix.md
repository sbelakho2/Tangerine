# Tangerine Feature Matrix

> Honest feature comparison: Tangerine vs Rust, derived from the executable
> state of the self-hosted compiler, not from declared module surfaces.
> Statuses are those of the [**Feature Registry**](feature_registry.md) —
> the single source of truth for one-status-per-feature. The registry is
> **generated evidence**: `features.toml` (machine-readable) is rendered
> into `feature_registry.md` by `scripts/gen_feature_registry.sh`, with
> every status mechanically derived from the test-file existence, the
> suite membership, and the declared CI gates; the CI evidence-gate job
> regenerates it and runs `git diff --exit-code`. Where this document and
> the registry disagree, the registry wins.

## Legend — status definitions

| Status | Meaning |
|--------|---------|
| **implemented + run-verified at SHA** | The compiler/runtime implements the feature AND an observed successful execution of its test artifact at the named commit is proven by a CI artifact (the `status-snapshot` generated by `scripts/gen_status.sh` from the tested SHA). **None in this snapshot** — no ladder/CI run has occurred on the tested tree |
| **implemented + test-covered** | The compiler/runtime implements the feature and a committed test artifact exists (manifest-registered canary, invariant group, required CI gate, `@test` file, or the self-host kernel as workload) that exercises it — but no observed execution at this SHA |
| **implemented + unverified** | The compiler/runtime implements the feature; no committed test artifact exercises it |
| **excluded-from-release** | The feature is explicitly REMOVED from the release surface (the reviewer's item 5 elimination): every non-implemented row carries this status — the old `partial` / `API-only` / `design` / `unsupported` vocabulary is gone. Either the surface was never implemented (declared/doc-only rows, the platform-only surfaces gated experimental), or the compiler's rejection surface IS the exclusion (the E100/E106 hard errors enforce the absence) |

Every row is exactly one of **implemented (+ test-covered / unverified)** or
**excluded-from-release**; the feature registry is the single status
authority (`features.toml` → `scripts/gen_feature_registry.sh` →
`feature_registry.md`).

## Kernel closure note

"Bootstrap closure" below means the 37 files in
`bootstrap/compiler_kernel.manifest` (14 std modules + the compiler kernel)
that the stage0→stage1 ladder compiles. Everything outside the closure is
**API-only** until it passes per-module native test suites. The E106
migration of the non-kernel stdlib is **COMPLETE** (2026-08-20): every
shipped `std/*.tg` module (the count is computed from the glob — currently
131; the reviewer's 133-module table included `std/postgres.tg`, since
merged into `std/db.tg`, and `std/hash_tests.tg`, removed) is parse-clean
under the current grammar, enforced by the two-layer gate
(`tests/run_stdlib_e106_sweep.sh` — `tg check` zero-diagnostics + the
forbidden-syntax grep backstop), a **required CI job** (`stdlib-e106-sweep`
in `.github/workflows/ci.yml`); the item-32 completeness model
([`stdlib_completeness.md`](stdlib_completeness.md)) assigns every module
to a verification family with a minimum proof, and its enumeration gate
fails on any un-contracted module. The item-33 stable-subset policy flags
the platform-only modules (wasm/gpu/embedded/simd/effects/android/ios/
cocoa/windows/gui/hal/kernel) experimental and excludes them from the
shipped-std behavior claims; see
[`stdlib_reference.md`](stdlib_reference.md) §Completeness.
