🍊 Tangerine Completion & Quality System (CQS)
Formal Specification – v0.2 Draft
1. Scope
The Completion & Quality System (CQS) defines:
Static detection of incomplete or risky implementations
Context-aware interpretation of those detections
Deterministic scoring of implementation completeness
Build-mode dependent enforcement rules
Structured reporting for both human developers and automated agents
CQS MUST:
Avoid AI or heuristic guesswork
Avoid rigid, one-size-fits-all rejection rules
Minimize false positives
Provide actionable feedback
Remain deterministic and reproducible
2. Definitions
2.1 Symbol
A function, method, struct, enum, trait, impl, or module.
2.2 Surface Class
Every symbol is automatically classified into one of:
PublicStable
PublicExperimental
InternalHotPath
InternalGlue
TestOnly
PlatformShim
Classification is defined in §3.
2.3 Evidence Signals
Deterministic, static or execution-derived indicators about implementation quality.
Signals are categorized into:
Control-flow signals
Data-flow signals
Error-handling signals
Coverage signals
Capability signals
Future/Feature-gate signals
2.4 Completeness Score
A numeric value in range [0, 100] computed per symbol.
3. Surface Classification Rules
Classification is computed at compile time.
3.1 PublicStable
A symbol is PublicStable if:
Declared pub
Not annotated @experimental
Not inside a module annotated @experimental
Referenced by at least one non-test external module OR exported
3.2 PublicExperimental
If:
Declared pub
Annotated @experimental OR
Module annotated @experimental
3.3 InternalHotPath
If:
Not public
Referenced ≥ N times (default N=5) OR
Annotated @budget OR
Annotated @hot
3.4 InternalGlue
If:
Not public
Thin wrapper (< X statements)
Mostly forwards to other calls
3.5 TestOnly
If:
Only referenced by test modules
3.6 PlatformShim
If:
Annotated @platform(...) OR
Entirely gated by cfg(...)
4. Evidence Signals
Signals are deterministic and computed via compiler passes.
4.1 Control-Flow Signals
Computed from Control Flow Graph (CFG).
CF-1: Unreachable Branch
A branch is unreachable if:
Its entry block has no predecessor
OR guard condition statically false
CF-2: Non-Exhaustive Match
Match expression missing known variants without explicit match_non_exhaustive.
CF-3: Panic/Unreachable Exit
Function exits via:
panic
unreachable
@unimplemented
CF-4: Constant Return Dominance
If return value is constant and:
Function has ≥1 parameter
Parameters not referenced in computation
Body contains no side-effecting calls
Signal raised.
4.2 Data-Flow Signals
Computed via Def-Use chains.
DF-1: Unused Parameter
Parameter never read.
DF-2: Output Independent of Inputs
Return value does not depend on any input parameters.
DF-3: Dead Assignment
Variable assigned but never read.
DF-4: All Branches Return Same Literal
All return paths produce identical literal or trivial constant.
4.3 Error Handling Signals
EH-1: Ignored Result Without Justification
A Result value is discarded without:
?

Comment/annotation

Requires tg test --coverage.

Branch in PublicStable symbol with zero coverage.

If a branch is eliminated, it simply disappears; expected arms are computed from the same anchoring pipeline, so IDs stay stable.

12) Determinism rules (normative)
To guarantee that ctxpack is identical across runs:
Candidate generation is stable-sorted by (node_id, edge_kind, neighbor_id).
Greedy ties are broken lexicographically by item_id.
Costs are computed deterministically:
cost_cu = ceil(byte_len(payload_json)/4) plus fixed overhead (default +10 CU per item)
Spans use byte offsets with stable file normalization.
Any truncation MUST be recorded in proof.truncation.
