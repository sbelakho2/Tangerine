1) Language definition essentials

These are “you don’t have a language without this.”

Lexical specification: tokens, whitespace, comments, Unicode policy, identifiers, literal rules

Grammar / syntax: unambiguous, versioned, with precedence/associativity rules

Semantics spec:

evaluation order (strict/lazy, short-circuit rules)

variable binding and scope rules

mutation rules

function call semantics

object/value model

lifetime rules (for Tangerine: ownership/borrowing)

Type system definition:

type forms (primitives, composites, generics)

inference rules

subtyping or no-subtyping rules

polymorphism model (traits/interfaces)

trait coherence rules

Control flow completeness:

conditionals

loops/recursion

early exit (return/break/next)

pattern matching (if supported)

Module system: namespacing, import rules, visibility, circular dependency policy

Error model:

Result/Option semantics

panic/abort semantics (and whether exceptions exist)

Standard library contract: what’s “in the language” vs “in packages”

Versioning / editions: how semantics evolve without breaking code

2) Compiler frontend must-haves

You can’t build a robust toolchain without these.

Lexer with precise spans and stable tokenization rules

Parser (with deterministic behavior)

AST definition (stable, versioned)

Error recovery (continue parsing to report multiple errors)

Diagnostics:

spans, notes, help, fix-its

stable error codes

machine-readable format (JSON output mode)

Source maps: mapping back from IR/codegen to source locations

Formatter support hooks (or a formatter integrated with the parser)

For Tangerine specifically:

block/closure parsing that preserves Ruby-ish ergonomics

macro syntax hooks (even if v0.1 minimal)

3) Name resolution & symbol system

This is where “toy language” becomes “real language.”

Symbol table with scopes (lexical + module)

Import resolution:

use handling

shadowing rules

ambiguity resolution

Visibility enforcement (pub, private)

Overload/method resolution rules

Monomorphization planning for generics (if AOT generics)

Incremental-friendly IDs (stable node/symbol IDs help tooling)

For Tangerine:

trait method lookup order (inherent vs trait) and ambiguity errors

orphan/coherence enforcement

4) Type checking & inference subsystem

Required for correctness and for tooling.

Type representation (interning, unification variables)

Unification engine

Inference algorithm (with principled rules, predictable)

Generic constraints (“where” clauses)

Trait solving (a solver)

Type-directed overload resolution

Error messages for types (expected vs found, “help” hints)

Type metadata for IDE (hover type, signature help)

For Tangerine:

type-checking integrated with borrow checking

trait coherence + overlap detection

5) Safety analysis (Tangerine-critical)

If the language claims Rust-like safety, this is core.

Move analysis (use-after-move detection)

Borrow checking (aliasing rules)

Lifetime/region inference

Drop safety (no drop while borrowed)

Thread-safety rules (Send/Sync-style)

unsafe boundary:

explicit syntax

linting/auditing hooks

restrictions by package policy

Optional but huge:

Effect system (side effects tracked)

Capability system (IO/network/process gated)

6) Mid-level IR (MIR) and lowering

A “real compiler” needs IR to optimize and reason about code.

Desugaring pass (surface syntax → core forms)

Typed mid-level IR

Explicit control flow graph

Explicit temporaries and drops

Verifier for IR invariants

Pretty printer for IR (debugging the compiler itself)

For Tangerine:

MIR must encode borrows, moves, drops, match lowering

7) Optimization pipeline

Not always required for “a language,” but required for “fast like Rust.”

SSA conversion (or an equivalent optimization-friendly IR)

Core optimizations:

constant folding/prop

DCE

inlining

CSE/GVN

loop opts (LICM, unrolling optional)

bounds-check elimination (when provable)

escape analysis / stack promotion

Debug vs release modes

Profile-guided options (later, but planned)

8) Code generation + linking

This is where it becomes an executable.

Target ABI compliance (platform calling conventions)

Lowering to machine code (LLVM or custom backend)

Register allocation (if custom backend)

Object file emission

Linker integration

Debug info emission (DWARF/PDB)

LTO support (optional early, but important)

Cross-compilation support (eventually “must-have” for a serious language)

For Tangerine:

deterministic builds (stable ordering, stable hashes)

predictable binary layout rules (for reproducibility)

9) Runtime system (even “no runtime” languages have one)

Even Rust has runtime components (panic, allocator hooks, etc.).

Allocator interface (alloc/realloc/free)

String/Array/Map representations

Drop glue / destructors

Panic strategy (abort vs unwind)

Threading primitives hooks

Backtrace support (debug)

FFI boundary (eventually)

Standard startup (main entry, args/env)

For Tangerine:

no GC by default

deterministic drop order

optional async runtime later

10) Standard library (minimum viable completeness)

A language without stdlib is not “full” for most users.

Must-have modules:

core primitives

formatting

collections

IO + filesystem

networking (at least TCP)

time

threading + sync

testing harness

process/env

error types

For Tangerine:

safe-by-default APIs (capability gating strongly recommended)

property testing/fuzz hooks (agent-friendly)

11) Toolchain: “real language” user experience

This is the big difference between “compiler” and “platform.”

Build tool / package manager

dependency resolution

lockfiles

build cache

workspace support

Testing tool

Benchmark tool

Formatter

Linter

Doc generator

Language server (LSP)

REPL (optional but very Ruby-spirit)

Installer & version manager

CI templates and reproducible build docs

For Tangerine:

“tg agent” workflows if you want to win the agent era

machine-readable diagnostics and structured metadata

12) Ecosystem & governance requirements (practical “fullness”)

These aren’t compiler passes, but you won’t succeed without them.

Language spec versioning and compatibility policy

Editions and migration tooling

RFC process

Security advisory process

Package registry policy

Stdlib stability guarantees

Test suite / conformance suite

Reference implementations and examples

Documentation and learning material

Coding style guide
