MCOT v3++ — ULTIMATE DEBUGGING + PORTABILITY + ERGONOMICS CHECKLIST (TXT)
Maximal Consistency, Optimization, Graphics/UI, Embedded & Web/WASM Test
PLUS: Ruby-like ergonomics checks, Rust-like speed & memory safety checks, and cross‑platform/OS/hardware compatibility checks
Applies to Stage‑2 (self‑hosted) toolchain only | Date: 2026-03-02

PURPOSE
  This checklist maximizes the probability of finding ALL practically discoverable bugs and
  makes every failure reproducible, minimized, categorized, and easy to debug.

  It avoids specifying surface syntax or enumerating language features; it tests semantics,
  invariants, performance/memory safety properties, cross‑oracle equivalence, determinism
  envelopes, ABI contracts, and platform portability.

  Guiding principle: NEVER accept a failure without:
    (1) deterministic reproduction,
    (2) minimal reproducer or minimal trace,
    (3) exact localization (stage/pass/boundary),
    (4) actionable evidence bundle (IR, certs, diffs, hashes, traces),
    (5) deduplication into a clustered root cause signature.

========================================================================================
0) ORACLES (INDEPENDENT CORRECTNESS CHECKS)
========================================================================================
[ ] Oracle A — Cross‑configuration equivalence:
      Baseline (C0) vs Aggressive (C3) vs Randomized legal schedules (Crand).
[ ] Oracle B — Translation validation:
      Each optimization pass emits a certificate; a verifier checks equivalence / invariants.
[ ] Oracle C — Differential execution:
      Native backend vs independent IR executor (interpreter/VM).
[ ] Oracle D — ABI boundary oracle:
      Interop & plugin boundaries: layout, calling convention, ownership, error mapping.
[ ] Oracle E — Deterministic replay oracle:
      Record → replay → identical outputs within envelope.
[ ] Oracle F — Graphics pixel oracle:
      CPU reference exact; GPU backends within strict envelope + structural hashes.
[ ] Oracle G — Embedded emulator oracle:
      Instruction trace and/or reference peripheral model transcript equivalence.
[ ] Oracle H — Cross‑platform equivalence oracle:
      Same program + same inputs + same comparator envelope must hold across supported OS/CPU targets.
[ ] Oracle I — Performance equivalence oracle:
      Optimized builds meet “Rust‑class” performance targets under defined benchmarks and budgets,
      and do not regress beyond policy thresholds.

========================================================================================
1) FAILURE HANDLING: FINDINGS MUST BE COMPLETE (NO EXCEPTIONS)
========================================================================================
Every failure becomes a Finding. A Finding MUST include:

IDENTITY
[ ] finding_id = sha256(canonical_fields)
[ ] category + severity + domain + stage
[ ] toolchain_id (edition + compiler hash + target triple)
[ ] config_ids (C0/C3/Crand + pass schedule seed(s))
[ ] corpus_source + program_id + input_id + generation seed

REPRODUCTION (MUST BE ONE‑COMMAND REPRODUCIBLE)
[ ] exact compile commands for each configuration/oracle
[ ] exact run commands for each oracle (including platform/target)
[ ] deterministic seeds & PRNG states captured
[ ] environment fingerprint:
      OS, kernel, libc, CPU model, CPU features mask, locale, timezone, file path policy,
      file system type, container image hash (if used), external tool versions,
      graphics backend version (if applicable), emulator/wasm runtime version (if applicable)

EVIDENCE BUNDLE (MANDATORY)
[ ] compiler stdout/stderr + structured diagnostics JSON (not just text)
[ ] full IR dumps for involved stages:
      - typed mid IR
      - post‑validation IR
      - pre/post each pass when needed
      - final IR feeding codegen
[ ] per‑pass pipeline trace:
      pass names, order, enabled flags, pass seeds, and timing/memory per pass
[ ] translation‑validation certificates for each pass + verifier results
[ ] binary/object hashes + normalized disassembly hashes (or IR hashes preferred)
[ ] runtime traces (domain‑specific):
      core outputs, UI events, web transcripts, embedded IO/peripheral transcripts, etc.
[ ] for graphics: render outputs + hashes + diff images + display‑list/layout hashes
[ ] for portability: platform matrix evidence (which OS/arch/hardware reproduced the issue)

DELTA ANALYSIS (MANDATORY FOR MISMATCHES)
[ ] comparator used (exact / ULP / pixel envelope / transcript hash / perf budget)
[ ] first divergence point (first differing byte/frame/event/tick/trace index)
[ ] minimal input / minimized program / minimized trace
[ ] related cluster linkage

TRIAGE TAGS (DETERMINISTIC)
[ ] stage tag: frontend | resolver | types | borrow | IR | opt | codegen | link | runtime
[ ] domain tag: core | gfx | ui | embedded | web | wasm | portability | performance | ergonomics
[ ] boundary tag: ABI | plugin | FFI | scheduler | allocator | file | net (if relevant)
[ ] implicated pass/invariant tag (when known)
[ ] platform tags: os=..., arch=..., cpu=..., libc=..., backend=...

========================================================================================
2) ERROR TAXONOMY (CATEGORIES) + SEVERITY RULES
========================================================================================
P0 (must fix before any release): crash/hang, miscompile, ABI violation, reproducibility break,
security boundary violation, embedded target corruption, memory safety violation, cross-platform divergence.

P1: IR invariant violations, translation validation failures, wrong accept/reject, major runtime
semantic violations, performance catastrophes (order‑of‑magnitude regressions).

P2: determinism envelope failures, diagnostic instability, UI layout/event routing inconsistencies,
portability edge cases that fail only on a subset of supported platforms.

P3: optimization regressions and quality-only deviations within noncritical budgets.

TOP‑LEVEL CATEGORIES (core)
  - COMPILER_CRASH, COMPILER_HANG
  - DIAGNOSTIC_MISMATCH, REJECTION_BUG
  - IR_INVARIANT_VIOLATION, LOWERING_MISMATCH
  - MISCOMPILE, PASS_CERT_FAILURE
  - ABI_VIOLATION
  - RUNTIME_SEMANTICS_BUG, NONDETERMINISM_BUG
  - REPRODUCIBILITY_BUG, TOOLCHAIN_INTEGRITY_BUG
  - OPTIMIZATION_REGRESSION
  - SECURITY_BOUNDARY_BUG

ADDITIONAL CATEGORIES (ergonomics/performance/portability)
  - ERGONOMICS_REGRESSION (Ruby-like usability: readability, consistency, diagnostics, refactors)
  - PARSER_AMBIGUITY_OR_STABILITY_BUG (grammar ambiguity; unstable parse under edits)
  - PERF_TARGET_MISS (fails “Rust‑class speed” thresholds on canonical benchmarks)
  - MEMORY_SAFETY_VIOLATION (any evidence of UB, invalid access, data race in safe code paths)
  - PLATFORM_DIVERGENCE_BUG (different observable behavior across supported OS/arch beyond envelope)
  - PLATFORM_TOOLCHAIN_INTEGRATION_BUG (install, dynamic linking, paths, permissions, sandboxing differences)

DOMAIN CATEGORIES (gfx/ui)
  - GFX_API_CONTRACT_BUG
  - GFX_BACKEND_ABI_BUG
  - GFX_RENDER_MISMATCH
  - GFX_TEXT_LAYOUT_BUG
  - UI_LAYOUT_INCONSISTENCY
  - UI_EVENT_ROUTING_BUG
  - COMPOSITOR_DAMAGE_BUG

DOMAIN CATEGORIES (embedded)
  - EMBEDDED_TARGET_BUG
  - EMBEDDED_MEMORY_MODEL_BUG
  - EMBEDDED_INTERRUPT_BUG
  - EMBEDDED_PERIPHERAL_MODEL_BUG
  - EMBEDDED_DETERMINISM_BUG

DOMAIN CATEGORIES (web/wasm)
  - WEB_SERVER_SEMANTICS_BUG
  - WEB_ASYNC_SCHEDULER_BUG
  - WASM_RUNTIME_BUG
  - WEB_INTEROP_ABI_BUG
  - WEB_RENDER_PIPELINE_BUG
  - WEB_SECURITY_POLICY_BUG

========================================================================================

[ ] Absolute paths normalized (strip build root from diagnostics/IR/debug info).
[ ] Locale fixed (LC_ALL=C), timezone fixed (UTC), deterministic temp paths.

[ ] Stable thread scheduling mode available (optional; recommended for concurrency debugging).
[ ] All external dependencies hashed and recorded (linker, libc, graphics libs, emulator, wasm VM).

PORTABILITY BASELINE (required)
[ ] Define supported platform matrix (OS × arch × libc/CRT × CPU families × GPU backends).
[ ] For each platform in the supported matrix:
    - same harness version
    - same corpus version
    - same seeds
    - comparable “envelope” comparators (see determinism section)
[ ] Record and publish platform matrix results with identical Finding IDs when reproducible cross-platform.

========================================================================================
Step 4.1 — Build Stage‑2

[ ] Build stdlib/runtime/tools needed by MCOT.

Step 4.2 — Triple self‑rebuild agreement

    - preferred: normalized typed IR hashes of outputs
    - acceptable: normalized object/assembly hashes with debug/path normalization.
[ ] Any mismatch → TOOLCHAIN_INTEGRITY_BUG (P0/P1).

Step 4.3 — Two-directory reproducible builds
[ ] Clean build in dir A and dir B.
[ ] Normalize timestamps/paths; compare artifacts.
[ ] Any mismatch → REPRODUCIBILITY_BUG (P0).

Step 4.4 — Bootstrap capsule
[ ] Build reduced compiler capsule (frontend + verifiers + minimal optimizer).
[ ] Run reduced MCOT subset with capsule.
[ ] Any mismatch/crash → TOOLCHAIN_INTEGRITY_BUG.

5) MCOT v3++ TRACKS — EXECUTION CHECKLIST
========================================================================================
NOTE: Every track MUST be run under:
  - C0 baseline
  - C3 aggressive
  - Crand randomized legal schedules (deterministic seed)
and must produce per-pass certificates where enabled.

----------------------------------------------------------------------------------------
5A) RUBY‑LIKE ERGONOMICS & FRONTEND STABILITY TRACK (NO SYNTAX DISCLOSURE)
----------------------------------------------------------------------------------------
Goal: ensure the language’s surface grammar and ergonomics are stable, predictable, and “fun”/productive.
These are tested via editing‑stability, parsing determinism, diagnostics clarity, and refactor safety.

Parser/edit stability
[ ] Incremental edit stability: small edits should cause local parse changes only (bounded AST delta).
[ ] Ambiguity detection: grammar ambiguity checks run in CI; ambiguous constructs must be rejected or disambiguated deterministically.
[ ] Precedence/associativity stability: parse tree must be stable under formatting changes.
[ ] Whitespace/comment robustness: inserting/removing whitespace/comments must not change semantics.
[ ] Diagnostic friendliness: errors must be localized, with stable codes and high-quality recovery.
[ ] IDE/LSP invariants: go-to-definition, rename, find-references must be consistent across platforms.

DSL and readability proxies (without specifying syntax)
[ ] “Readable API layer” tests: validate that common patterns can be expressed without excessive ceremony
    (measured as: average AST node count per semantic operation in representative corpus).
[ ] “Refactor friendliness” tests: large-scale rename/move/extract operations must preserve behavior under Oracles A/C.

Failures in this track are categorized as:
  PARSER_AMBIGUITY_OR_STABILITY_BUG, DIAGNOSTIC_MISMATCH, ERGONOMICS_REGRESSION

----------------------------------------------------------------------------------------
5B) CORE SEMANTICS TRACK (Oracles A/B/C)
----------------------------------------------------------------------------------------
[ ] Spec-Trace POSITIVE programs:
    - compile+run under C0/C3/Crand
    - compare outputs (Oracle A)
[ ] Spec-Trace NEGATIVE programs:
    - must be rejected
    - diagnostics must match expected codes/classes/spans
[ ] IR dump and verify at EVERY internal boundary (typed IR, validated IR, pre/post major phases)
[ ] Differential execution (Oracle C) for representative set:
    - run via IR executor and compare with native results
[ ] Translation validation certificates required; verify all (Oracle B)

----------------------------------------------------------------------------------------
5C) RUST‑LIKE MEMORY SAFETY TRACK (NO IMPLEMENTATION DETAILS)
----------------------------------------------------------------------------------------
Goal: ensure safe code cannot cause memory corruption, data races, or undefined behavior.
This track assumes the language promises strong memory safety properties.

Safety invariants
[ ] “Safe code UB ban”: any evidence of UB in safe-only corpus is MEMORY_SAFETY_VIOLATION (P0).
[ ] Lifetimes/aliasing invariants validated at IR boundaries (verifiers must prove rules hold).
[ ] Move/ownership invariants validated under metamorphic transforms and generative corpus.
[ ] Concurrency safety invariants: safe-only concurrent programs must not exhibit data races or torn reads.

Dynamic safety validation (black-box, no syntax)
[ ] Run runtimes under memory corruption detectors where feasible (address/bounds/poison checks),
    and treat any triggered corruption as MEMORY_SAFETY_VIOLATION.
[ ] Stress destructor/resource lifetime correctness (double-free/use-after-free cannot occur in safe corpus).
[ ] Cross-oracle safety: IR executor and native output must match AND no safety alarms can trigger.

FFI boundary safety
[ ] Any unsafe/boundary entry must be audited by ABI oracle (Oracle D) and taint/validation checks.
[ ] Ensure tainted inputs are validated before reaching sensitive sinks (domain-specific policies).

----------------------------------------------------------------------------------------
5D) OPTIMIZER MAX‑STRESS + RUST‑LIKE SPEED TRACK (Oracles A/B/C + Perf Oracle I)
----------------------------------------------------------------------------------------
Correctness (soundness)
[ ] Canonical schedule vs Crand schedules: outputs must match baseline.
[ ] Per-pass translation validation certificates required; verify all.
[ ] Pass order delta debugging on mismatch; region delta debugging to minimal IR region.

Performance (speed)
[ ] Canonical benchmark suite (micro + macro) with stable inputs:
      - compute kernels
      - allocation-heavy workloads
      - concurrency workloads
      - IO-bound workloads (measured as logical events, not wall time, where possible)
[ ] Performance budgets:
      - runtime p50/p95 thresholds
      - allocation counts/bytes thresholds
      - binary size thresholds
      - compile time thresholds
[ ] Cross-compiler consistency: performance characteristics should not vary wildly across platforms for same CPU class.
[ ] Regression detection uses robust stats (median + MAD) and fixed seeds.

Classification
[ ] Correctness divergence → MISCOMPILE / PASS_CERT_FAILURE
[ ] Budget miss (without correctness issue) → PERF_TARGET_MISS or OPTIMIZATION_REGRESSION

----------------------------------------------------------------------------------------
5E) ABI BOUNDARY + CROSS‑PLATFORM TOOLCHAIN INTEGRATION TRACK (Oracle D + H)
----------------------------------------------------------------------------------------
Goal: ensure code and artifacts behave consistently across OS/hardware and integrate cleanly.

ABI and linking
[ ] Layout probes: sizes, alignments, field offsets for all ABI-visible types.
[ ] Call probes: argument passing, return passing, sret behavior, stack alignment.
[ ] Ownership probes: handle lifecycle accounting, leak checks, invalid free protection.
[ ] Error mapping probes: boundary errors map to stable codes/messages.
[ ] Dynamic loading rules tested where applicable (path search, permissions, sandbox constraints).

Cross‑OS path/permissions semantics
[ ] File path normalization tests: separators, case sensitivity, reserved names, max path lengths.
[ ] Permission model differences: ensure behavior matches spec under least privilege.
[ ] Line ending differences: source mapping and diagnostics remain correct.
[ ] Locale/Unicode filesystem tests: identifiers and file names stable and correctly handled.

Hardware variability
[ ] CPU families: validate same outputs across x86_64 and arm64 within allowed numeric envelopes.
[ ] SIMD variability: verify vectorized code produces identical results under strict comparators.
[ ] Endianness policy: if any non-little-endian target is supported, include equivalence tests; otherwise ensure unsupported targets fail gracefully.

Failures → PLATFORM_DIVERGENCE_BUG or PLATFORM_TOOLCHAIN_INTEGRATION_BUG

----------------------------------------------------------------------------------------
5F) GRAPHICS/UI TRACK (Oracles A/D/E/F)
----------------------------------------------------------------------------------------
CPU Reference (required):
[ ] CPU raster backend is authoritative pixel oracle (exact hash).

Render contract kernels:
[ ] state stack nesting, transform composition, clip stack correctness
[ ] paint and stroke properties (caps/joins/dashes), image mapping/filtering/blend
[ ] glyph run rendering contract and bounds

UI toolkit:
[ ] layout invariants: measure/layout stability, constraints satisfaction, no negative sizes
[ ] event routing invariants: hit testing, focus, IME events, pointer capture
[ ] compositor invariants: damage tracking (no stale pixels), caching correctness

Deterministic replay:
[ ] record UI event stream + timers → replay → compare display-list + layout hashes + pixel outputs.

GPU backends (if enabled):
[ ] must match CPU oracle within envelope (≤ 1 LSB per channel sRGB) AND structural hashes match.
[ ] capture GPU command stream/pipeline/resource logs on mismatch.

----------------------------------------------------------------------------------------
5G) EMBEDDED TRACK (Oracles A/D/E/G)
----------------------------------------------------------------------------------------
[ ] Freestanding build validation: section/startup/no host deps.
[ ] Emulator oracle: deterministic instruction trace + peripheral transcript; replay equivalence.
[ ] Interrupt/concurrency stress: adversarial injection schedules; validate invariants.
[ ] Peripheral model conformance: register ordering/atomicity; transcript equivalence.
[ ] Cross-config equivalence: C0 vs C3 must match transcripts.

----------------------------------------------------------------------------------------
5H) WEB/WASM TRACK (Oracles A/C/D/E)
----------------------------------------------------------------------------------------
[ ] Server transcript tests: deterministic request/response transcripts; streaming/backpressure invariants.
[ ] Async scheduler replay: deterministic schedule, cancellation/fairness invariants, bounded deadlock exploration.
[ ] WASM tests: deterministic wasm runtime, host binding ABI correctness, memory/table invariants, compare vs native where possible.
[ ] Browser-shell render pipeline (if present): layout/paint/compositor invariants + pixel oracle.
[ ] Security policy tests (if applicable): sandbox/origin/capability invariants.

========================================================================================
6) ROBUSTNESS: NO CRASH, NO HANG, NO UB
========================================================================================
[ ] Compile fuzz: random bytes input → no crash, structured diagnostics only.
[ ] Structured fuzz: well-typed IR fuzz → optimizer/verifiers no crash/hang.
[ ] Timeouts: every compile/run bounded; timeout → COMPILER_HANG with full evidence.
[ ] Memory pressure: constrained heap; ensure controlled OutOfMemory errors.
[ ] Cross-platform robustness: run fuzz seeds on multiple OS/arch to find platform-only crashes.

7) DETERMINISM & COMPARATORS (STRICT RULES)
========================================================================================
Core outputs:
[ ] exact byte-for-byte

Numeric:
[ ] exact where mandated; ULP-bounded where permitted; record tolerances per case

Graphics:
[ ] CPU: exact hash
[ ] GPU: display-list hash AND layout hash + raster envelope ≤ 1 LSB per channel sRGB

Embedded:
[ ] exact transcript/trace hash; timing encoded as logical events if relevant

Web:
[ ] exact transcript hash; exclude real time; scheduler replay requires exact schedule+output

Reproducible builds:
[ ] normalized artifact hashes exact across dirs and across OS (where supported)
